## 1. 확정: 판넬·성별·사이즈 확인 기준 모두 90%

| 항목 | 현재 코드 기본값 | 확정한 새 기준 |
| --- | --- | --- |
| 판넬 위치 | 50% | 90% |
| 성별/성인·아동 분류 | 95% | 90% |
| 사이즈 분류 | 95% | 90% |

- 사용자가 판넬도 90%로 하자는 제안을 승인했습니다. 점수 기준을 바꾸는 요청이며, 모델을 재학습하거나 정답률 90%를 보장하라는 요청이 아닙니다.
- 후보 자동 입력, 기존 수동 입력 보존, 빈 카테고리 ‘자켓’ 기본값, 아동 성별 필수 확인, 미인식 빈칸 확인은 유지합니다.
- 관련 코드: `coatdesk_v2/recognition.py`의 `DEFAULT_THRESHOLDS`, `Backend.setAiThresholds`와 저장 설정 `ai_thresholds`, `Garment.analysis_review_keys`/`apply_analysis`/`pending_review`.
- 새 기본값만 바꾸면 이전 설치의 저장된 설정이 남을 수 있습니다. 기존 작업에서도 새 기준 적용과 확인 상태 갱신이 가능하도록 저장 설정·재분석 경로를 확인해야 합니다.

### 확인된 문제: 예전 확인 필요 사유가 누적됨

- `Garment.apply_analysis()`가 `review_required`를 기존 값과 합집합으로 저장합니다.
- 실제 재현: 사이즈 점수 93.8%에서 기준 95%로 확인 필요를 만든 뒤, 기준 90%의 새 분석 결과로 `held=[]`를 적용해도 과거 `size` 확인 표시가 남습니다.
- 새 점수 기준으로 분석하면 현재 유효한 확인 사유를 다시 계산해야 합니다. 과거 기준 때문에 남은 표시와 현재도 필요한 검수를 구분하고, 사람이 수정한 값·확인 기록·아동 성별 검수는 보존해야 합니다.
- 기준을 충족한 완성 항목은 별도의 전체 확인 없이 완료가 되고, 기준 미달·미인식 항목만 필요한 검수를 요구해야 합니다.

참고 근거(기존 촬영 묶음의 회귀 자료이며 새로운 독립 검증 아님): 924벌의 판넬 점수에서 90% 미만은 40벌, 95% 미만은 74벌입니다. 사용자 앞서 본 40벌에서 성별·사이즈 기준만 95→90으로 재계산하면 확인 대상 14→1벌이지만 판넬 기준을 올린 결과와는 구분해야 합니다. 결과 파일은 `model-results/20261026-panel-detector-v2/predictions.json`에 있습니다.

## 3. 조작 불편사항 — 사용자 추가 요청

### 최우선 확정: 옷 선택 없이 방향키로 연속 페이지 이동

사용자가 가장 심각한 문제로 보고한 내용:

1. 현재 페이지를 넘기려면 하단 다음 버튼을 마우스로 눌러야 합니다.
2. 방향키는 보이는 옷 4벌 중 하나를 클릭해 선택한 뒤에야 동작합니다.
3. 페이지를 넘기면 선택이 풀린 것처럼 되고, 다음 방향키를 쓰려면 다시 옷을 클릭해야 합니다.
4. 마우스로 옷 분류를 바꾸고 키보드 방향키로 바로 다음 페이지를 보는 흐름이 끊깁니다. 현재 키보드 방식이 마우스보다 번거롭습니다.

**확정한 목표:** 작업 화면에서 옷 선택 여부와 관계없이 왼쪽/오른쪽 방향키로 이전/다음 페이지를 연속 이동합니다. 매 페이지에서 클릭하거나 특정 옷을 선택할 필요가 없어야 합니다. 마우스로 카테고리를 수정한 뒤에도 별도 사진/배경 클릭 없이 방향키를 사용할 수 있어야 합니다. 옷을 여러 벌 선택하는 기능과 페이지 이동 키 사용 조건은 분리합니다.

코드에서 확인한 사실과 원인 후보:

- `Main.qml`의 `board`에 `Keys.onLeftPressed/onRightPressed/onUpPressed/onDownPressed`가 붙어 있어 키 이벤트가 해당 영역에 도달해야 합니다. 전역 페이지 이동 키 처리는 없습니다.
- `GarmentCard.qml`의 사진 선택은 `card.forceActiveFocus()`를 호출합니다. `Choice.qml`의 ComboBox/TextField는 자체 키보드 포커스를 가집니다.
- `Backend.pageBy()` → `_refresh(False, False)` → `PageModel.replace()`에서 페이지의 코드 집합이 바뀌면 모델을 reset하며 화면 delegate가 다시 만들어집니다. 이때 활성 포커스가 사라지는지 다음 세션에서 재현해야 합니다.
- `pageBy()`에 선택 집합을 직접 비우는 코드는 없습니다. 사용자가 느낀 ‘선택 해제’와 키 입력 포커스 상실을 구분해 진단합니다. 단순히 매 페이지 임의의 옷을 자동 선택하는 방식으로 우회하지 않습니다.

필수 완료 조건:

- 작업공간을 열자마자 옷 클릭 없이 →→→, ←←←로 연속 이동합니다.
- 카테고리를 마우스로 선택해 적용하고 목록을 닫은 즉시 →로 다음 페이지를 볼 수 있습니다. 닫힌 콤보에 포커스가 남았다는 이유로 방향키가 카테고리 값을 바꾸면 안 됩니다.
- 카드 확인·필터·사진만 보기 전환·마우스 페이지 버튼 사용 후에도 불필요한 재클릭 없이 이어서 이동합니다.
- 빠르게 여러 번 입력해도 한 키 입력이 두 번 처리되지 않고, 첫/마지막 페이지에서 범위를 벗어나지 않습니다.
- 페이지 전환 전에 수정한 값이 저장되고, 기존 여러 벌 선택·실행 취소·작업별 보기 상태를 깨뜨리지 않습니다.
- 사진+입력 보기와 사진만 보기, 전체/확인 필요/검색/분류 필터 상태에서 각각 확인합니다.
- 대화상자·확대 화면이 열린 동안 배경 페이지까지 동시에 이동하지 않습니다.

키 충돌을 피하기 위한 **구현 제안(상세 동작은 확정 전 구분)**: 드롭다운 목록이 열린 동안의 항목 이동, 검색/작업 이름 등 실제 텍스트 편집 중인 커서 이동, 확대 화면의 이전/다음 옷 키는 해당 컨트롤에서 처리하고, 목록 선택·입력 완료 후에는 작업 페이지 키를 다시 쓸 수 있게 합니다. 사이즈는 아래 새 요청에 따라 자유 입력을 제거합니다. 사용자는 모든 텍스트 편집 중의 방향키까지 페이지 이동으로 바꾸라고 요청한 것은 아닙니다. 필요하면 구현 전 이 경계만 확인하며, 옷을 먼저 선택해야 하는 기존 조건을 다시 도입하지 않습니다.

### 확정: 앱 조작·화면 전환의 반응 속도 최적화

- 사용자가 “앱 자체가 좀 느린 것 같다”고 보고했고, 후속으로 **분석 시간 최적화가 아니라 작업공간으로 넘어갈 때 등 앱 전체 조작을 빠릿하게 해 달라**고 범위를 명확히 했습니다. 이 항목은 확정된 구현 요청이며 현재 세션은 다음 세션용 문서만 갱신합니다.
- **우선순위:** 홈에서 작업공간 열기 → 열린 작업 탭 간 전환/홈 복귀 → 연속 페이지 이동 → 선택창·메뉴·배치 팝업 열기 → 분류 수정·필터·보기 전환 후 화면 반응. 첫 진입과 이미 열었던 화면 재진입을 나눠 측정합니다.
- 분석 모델·가중치·추론 계산·분석 총 소요시간·학습 성능은 최적화 대상에서 제외합니다. 분석 중에도 화면이 멈추지 않게 하는 UI 갱신 경로는 이 요청의 대상입니다.
- 현재는 구체적인 지연 시간·사진 수·발생 구간을 측정하지 않았으므로 원인을 단정하거나 이미 빨라졌다고 주장하지 않습니다. 키보드 포커스 때문에 입력이 무시되는 현상과 실제 처리 지연도 구분합니다.
- 코드 확인: `openWorkspace()`가 호출 스레드에서 이전 보기 저장·`Repository.load()`·설정 저장·`_refresh()`를 연속 실행합니다. `Repository.load()`는 해당 작업의 전체 옷 JSON을 읽어 객체로 만듭니다. `Backend.state`는 상태를 읽을 때 `recent()`를 두 번 호출하고 설정 조회도 수행합니다. 이 작업들이 UI 이벤트 처리에 얼마나 영향을 주는지 측정한 뒤 필요한 부분만 개선합니다.
- 추가 조사 지점: `PhotoPane.qml`의 비동기 이미지 읽기/표시 크기/캐시, `images.py`, `Backend._refresh()`의 전체 항목 순회·모델 갱신, `pageBy()`의 `_view()` 저장, 분석 진행 이벤트마다 전체 작업을 다시 읽는 `_event()` 경로.
- 개선 후보는 중복 DB 조회·전체 재계산 줄이기, 변경된 카드/목록만 갱신하기, 사진 재사용과 제한된 인접 페이지 미리 읽기, 무거운 로딩과 화면 응답 분리 등입니다. 병목이 확인되지 않은 후보를 모두 도입하거나 임의의 새 캐시·서버·프레임워크를 추가하지 않습니다.
- 위 코드는 조사 후보이며 측정으로 병목이 확인된 부분만 수정합니다. 분석 모델 정확도나 사용자의 자동 저장을 희생하는 변경을 임의로 넣지 않습니다.
- 같은 사진·작업·PC에서 변경 전후 작업공간 전환, 페이지 이동, 선택창 열기, 입력 후 반응 시간을 비교해 기록합니다. 버튼 클릭부터 첫 화면 표시까지와 사진 표시 완료까지를 분리해 측정합니다. 사진 교체 중에도 버튼/키 입력이 멎지 않아야 하며, 이전 페이지 재방문 시 불필요한 재읽기·깜빡임이 있는지도 확인합니다.
- 빠른 작업 전환 중 이전 작업의 로딩 결과가 새 작업에 섞이지 않고, 입력·검수·실행 취소·선택·필터·작업별 보기 상태가 유지돼야 합니다. 자동 저장의 안전성을 떨어뜨리거나 무제한 사진 캐시로 메모리를 키우는 방식으로 속도를 맞추지 않습니다.
- 긴 화면 전환 애니메이션·효과로 대기 시간을 늘리지 않습니다. 새 파란 디자인·빠른 입력·격자 배치·연속 방향키와 통합한 설치본에서 최종 확인합니다.

### 위치 확정: ‘사진만 보기’ — 승인 A 시안의 상단 도구줄

- 사용자는 하단 페이지 이동/상태 표시줄 맨 오른쪽의 ‘사진만 보기’ 위치가 이상하다며 이동을 요청했고, 새 위치를 제안해 달라고 했습니다.
- **A 시안 승인으로 확정:** 상단 작업 도구줄의 오른쪽에 `[사진+입력 | 사진만 보기]`의 두 칸 선택을 두고 그 오른쪽에 배치·검색·분류를 둡니다.
- 추천 배치: `[분석] [확인 필요 N] … [사진+입력 | 사진만 보기] [옷 번호 검색] [분류 ▼]`.
- 사진 영역과 연결된 보기 전환을 상단에 모으고, 하단은 페이지 이동·진행 상태 표시 용도로 사용합니다. 기본 모드는 기존 사진+입력으로 유지합니다.
- 1000×720 창에서 한 줄 도구들이 겹치거나 잘리지 않아야 합니다. 승인 시안의 구성은 유지하되 좁은 폭에서 읽히는 크기와 간격을 조정합니다.

### 확정: ‘외투 작업실’ 상단 제목 띠 제거 / 하단 홈 이동

- 사용자는 앱 내부 최상단의 ‘외투 작업실’ 제목과 부제 영역이 불필요하므로 제거해 달라고 했습니다. Windows가 그리는 창 제목 표시줄을 제거하라는 요청은 아닙니다.
- 제거 대상은 `Main.qml`의 높이 62인 `header: Rectangle`입니다. 작업별 이름·촬영일·수량·자동 저장/작업 메뉴가 있는 별도 줄은 이 요청의 제거 대상이 아닙니다.
- **A 시안 승인으로 확정:** 하단 작업 탭 줄의 맨 왼쪽에 `[홈]`을 고정 배치합니다. 그 오른쪽에 열린 작업 탭과 `+`를 두어 홈과 날짜 작업 사이 이동을 한곳에 모읍니다.
- 홈 버튼은 작업 탭이 가로 스크롤돼도 사라지지 않도록 고정합니다. 홈 이동으로 열린 작업·입력·검수·작업별 보기 상태가 닫히거나 초기화되지 않아야 합니다.
- 기존 상단 제목 클릭에 연결된 홈 이동을 대체하고, 첫 실행은 종전처럼 홈에서 시작합니다. 버튼 위치·표시는 승인한 A 시안을 기준으로 합니다.

### 확정: 사이즈는 엑셀 허용 목록의 선택형 입력만 사용

- 사용자는 사이즈도 정해진 범위만 쓰므로 직접 입력칸을 없애고 카테고리·성별처럼 선택창으로 바꾸라고 요청했습니다. 예전 README/설계의 사이즈 자유 입력 허용보다 이번 요청이 우선합니다.
- 원본 `C:/Users/playj/Downloads/2025외투리스트_업로드서식EX_입력.xlsx`의 `양식예시(복사해서 사용)` 시트 I3 유효성 검사와 내장 `resources/standard_sheet.json`의 같은 칸에서 허용 목록을 읽어 확인했습니다.
- **확인한 허용값은 8개:** `2XS`, `XS`, `S`, `M`, `L`, `XL`, `2XL`, `3XL`. 원본의 유효성 검사 수식은 `"2XS,XS,S,M,L,XL,2XL,3XL"`입니다.
- 아동 `60/70`, `80/90`, `100/110`, `120/130`, `140/150`, `160`, `170`은 Q:R 보조 대응표의 표기이며 I열 입력 목록과 구분합니다. 인식 엔진은 이를 이미 위 8개 문자 사이즈로 변환합니다. 사이즈 선택 목록에 아동 숫자 표기를 임의로 추가하지 않습니다.
- 현재 `Choice.qml`의 사이즈는 `editable: true`로 별도 TextField를 쓰며 `domain.validate_fields()`는 `size`만 목록 검사를 생략합니다. `coatdesk.domain.OPTIONS.size`에도 위 8개 외에 일부 아동 표기가 섞여 있습니다. 카드만 바꾸지 말고 공유 허용값·필드 검증·일괄 입력·필터·엑셀 저장 검증의 기준도 일치시켜야 합니다.
- 미입력은 ‘선택’ 상태로 남길 수 있지만 저장 준비 완료로 취급하지 않습니다. 사용자가 선택을 마치면 방향키로 페이지 이동할 수 있어야 합니다.
- 기존 개인 DB에 이미 있는 목록 밖 값을 무단 삭제·임의 변환하지 않습니다. 실제 존재 여부를 확인하고, 해당 값은 목록에서 다시 고르도록 안내하며 기존 입력을 보존하는 처리 경로를 정합니다. 새 수동 입력과 새 저장에는 허용 목록을 적용합니다.

### 확정: 검수·사진만 보기 모두 표시 행/열 개수를 사용자가 선택

- 사용자는 사진만 보기뿐 아니라 **검수 화면에서도 동시에 볼 옷 개수를 선택**하고 싶다고 했습니다. 한글의 표 삽입처럼 작은 격자에서 원하는 행/열을 선택하는 팝업을 제안했습니다. 첨부처럼 많은 칸은 필요 없다고 했습니다.
- 참고 이미지: `.local/ui-followup-20261027/grid-layout-reference.png` (Git 제외). 이 이미지는 행/열 선택 상호작용의 참고이며 한글의 리본 UI 전체를 복제하는 요청은 아닙니다.
- 현재 검수 화면은 보기 설정의 2벌/4벌 라디오만 지원합니다. Backend는 `cards`를 2 또는 4로 제한하고 QML은 검수 화면을 2열로 고정합니다. 사진만 보기는 정면 기준 3열×줄 수 또는 각도 3장 묶음 기준 한 줄 1벌이므로 임의 행/열 선택은 아직 구현되지 않았습니다.
- **관리자 구체안(승인 대기):** 상단 보기 전환 옆에 `[배치 2×2 ▾]`를 두고, 누르면 최대 3×3의 작은 격자를 펼칩니다. 마우스를 올리면 좌상단부터 해당 범위를 강조하고 `2행 × 3열 · 6벌`처럼 보여 주며 클릭으로 확정합니다. 2열×2행=4벌, 3열×2행=6벌, 3열×3행=9벌 등을 고를 수 있는 방향입니다.
- 격자 1칸의 단위는 사진 장수가 아닌 **옷 1벌**입니다. 각도 3장 보기에서도 3장을 별도 옷 3벌로 계산하지 않습니다. 화면·입력란이 좁아지는 조합은 비활성화하거나 안내하며 최소 카드 크기와 허용 최대 행/열은 실제 1000×720 및 큰 창 검증 후 확정합니다. 3×3은 제안이며 검수 화면에서 무조건 9벌을 강제하라는 뜻이 아닙니다.
- 사진+입력과 사진만 보기의 배치를 각각 기억하고 모드를 오갈 때 복원하는 것을 제안합니다. 기존 작업별 저장 설정은 호환되게 읽고, 배치 변경 후 페이지 수·현재 옷·필터·방향키 페이지 이동이 일관돼야 합니다.
- 격자를 키보드로 조작 중에는 그 팝업만 처리하고 배경 페이지가 동시에 넘어가지 않아야 합니다. 팝업을 닫은 뒤에는 옷 재선택 없이 페이지 이동을 이어갑니다.
- 추천 도구줄 결합: `[분석] [확인 필요 N] … [사진+입력 | 사진만 보기] [배치 2×2 ▾] [번호 검색] [분류 ▼]`. 좁은 창에서 겹치면 표시 문구·배치를 조절하되 사진 공간을 불필요하게 줄이지 않습니다.

### 디자인 확정: 파란색 A 시안 기준

- 네 가지 생성 시안을 비교한 뒤 사용자가 **파란색 A 시안**을 선택했고 “딱 너가 만든 이미지처럼 하면 괜찮을 것 같다”고 승인했습니다. 토스의 구체적인 화면·로고·브랜드 자산을 그대로 복제하는 요청은 아닙니다.
- **승인한 시각 기준:** [파란색 A 시안](design/approved-blue-review.png). 다른 세션도 이 이미지를 직접 열어 확인합니다. 원본 `.local/ui-concepts-20261027/A-clean-blue.png`와 생성 프롬프트 `prompts.md`는 로컬에 추가 보관합니다. 이미지의 옷 사진·문구는 생성된 비교용 예시이며 실제 사용자 사진이나 작업 데이터가 아닙니다. 업무 데이터·기능 계약은 실제 코드와 이 문서의 사용자 요구사항을 따릅니다.
- A 시안의 라이트 전용 흰색/옅은 회색 바탕, 파란 주요 버튼·선택 상태, 얇은 구분선, 부드러운 카드와 입력 선택창, 글자 위계·간격을 기준으로 구현합니다. 현재의 진한 테두리·작은 기본 컨트롤·빽빽한 배치를 정돈합니다. 생성 이미지의 픽셀·사진 예시를 앱에 그대로 붙이는 방식이 아니라 실제 QML 컨트롤로 구현합니다.
- 사진과 업무 입력값을 중심으로 두고, 제목·라벨·부가 설명의 크기/색상/간격을 구분합니다. 둥근 카드나 여백 때문에 사진이 작아지거나 한 페이지 표시 개수가 불필요하게 줄지 않도록 합니다.
- 버튼·선택창·격자 팝업·대화상자의 높이, 모서리, 포커스/hover/선택 상태를 일관되게 맞춥니다. 홈의 작업 카드, 작업 화면, 새 작업 창, 엑셀 저장 창까지 같은 기준을 사용합니다.
- 필수 확인은 노란 강조 등으로 분명히 구분하고 오류·비활성·미입력·완료 상태의 가독성을 유지합니다. 겉모습만 바꾸며 확인 사유·입력 항목을 숨기거나 다크 모드를 다시 도입하지 않습니다.
- A 시안에 포함된 상단 제목 띠 제거, 하단 홈/작업 탭, 상단 사진+입력/사진만 보기·배치·검색·분류 조작을 기본 배치로 사용합니다. 앞서 상세 동작이 미정인 격자의 최대 크기·최소 카드 크기 등은 실제 창 크기 검증 후 정합니다. 선택형 사이즈와 선택 없이 연속 방향키 페이지 이동을 함께 반영하고, 긴 전환 애니메이션으로 체감 반응을 늦추지 않습니다.
- 구현 스택은 기존 PySide6/Qt Quick/QML을 유지합니다. 스타일을 바꾸기 위해 웹 프레임워크·새 UI 라이브러리·서버를 도입하지 않습니다. 폰트도 현재 설치 환경에서 사용 가능한 것을 우선합니다.
- 홈·새 작업/저장 창 등 A 이미지에 없는 화면도 같은 공통 스타일로 맞춥니다. 이 문서 작성에서는 디자인 코드·설치파일을 변경하지 않았습니다.

### 확정: 일반 선택창 + 별도의 빠른 입력 모드

- 사용자 목표는 **이미 입력된 분석값이 맞는지 최대한 빠르게 확인하고, 틀린 값만 적은 클릭으로 수정**하는 것입니다.
- 사용자는 현재 각 선택창을 클릭해야 목록이 열리는 점을 지적했고 호버 목록 또는 빠른 입력 모드를 문의했습니다. 이후 관리자가 제안한 **일반 모드의 선택창과 빠른 입력 모드의 펼친 선택 버튼 조합**에 “그렇게 하는 걸로”라고 승인했습니다.
- 일반 모드는 승인 A 시안의 선택창을 유지합니다. 빠른 입력 모드를 켜면 카테고리 `[자켓/코트/조끼/기타]`, 성별 `[남성/여성]`, 연령 `[성인/아동]`을 작은 버튼 묶음으로 보여 주고 한 번 클릭해 값을 저장합니다. 화면의 아동 표시는 기존 저장값 `유아동`과 일관되게 대응합니다.
- 사이즈는 허용된 8개 값만 작은 선택 격자로 제공합니다. 현재 선택값은 파란색으로 명확히 보여 주고, 낮은 점수 등 필수 검수 대상은 노란 강조와 구분합니다. 격자 크기·버튼 간격은 실제 카드 폭에 맞춰 정리합니다.
- 기본 조작은 **사진과 입력값 확인 → 틀린 값만 한 번 클릭해 수정 → 방향키로 다음 페이지**입니다. 별도 목록 열기 클릭이나 옷 선택 클릭을 요구하지 않습니다.
